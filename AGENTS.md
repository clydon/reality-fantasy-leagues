## UI/UX review direction

Before continuing the full-app review or mock, read [the fresh-start design brief](docs/APP-REVIEW-DESIGN-BRIEF.md). It captures the intended experience, skill responsibilities, state coverage and reuse requirements. Present one redesigned page with its relevant situation variants, then pause for the user's review before extending that design across the app. Existing mockups are reference material, not assumed approval.

An episode reveal applies across **all of the person's games for that episode**, with a full-screen visual recap and game/player results. Do not reintroduce per-game reveal selection from the superseded V3 mock. Tonight's order is identity/progress/people and watch controls, last-episode recap/reactions/discussion, then game updates; a small prominent top strip opens due game decisions or confirms readiness.

The 2026-11-12 component direction emphasizes **expressive data representation**, not decorative slogans or theatrical matchup graphics. The user likes the bold round's season overview A; the requested redesign also includes the actual Update episode popup. Compare shared viewing timelines (self, friends, latest release and next airing), and show one's own and permitted opponents' lineups with contributions, graphs and collapsible detail. Include the connected expanded, scoring and episode-position views. See [the data round](docs/show-soul-review/tonight-data-round3-2026-11-12.md). Earlier alternatives remain references, not blanket approval.

Use the reusable [UI Atlas](docs/UI-ATLAS.md) for source inventory, state/data fixtures, current/mock comparisons and focused design context before repeating a broad codebase scan. Start with `npm run ui:atlas` or `node scripts/ui-atlas.js inspect --case <id> --lens intent|impeccable|pfd`. Source discovery is not proof of rendered or verified state coverage; record missing adapters explicitly.

For generated-game UI work, use the [gameplay coverage matrix](docs/GAMEPLAY-COVERAGE.md) at `/__atlas/gameplay` and `node scripts/gameplay-matrix.js inspect <feature-id>` before rescanning the engine. Track creation/preview, mini, quick, full, detail and reveal coverage against quantity/content/privacy/lifecycle profiles. Compiler witnesses are not rendered fixtures or UX passes. Validate limits in actual show/sport context; record current fixture and artifact evidence for scoped gates. Proposed constraints do not enforce game restrictions. Start with one reviewable slice, then pause before extending its design.

The [Gameplay bench](docs/GAMEPLAY-BENCH.md) at `/__atlas/bench` is the executable lineup pilot. Reuse its seeded generator, real-engine projections/commands, production renderer and replay exports. `node scripts/gameplay-bench.js generate --seed=42 --out=.ui-atlas/fixture-v1.json` generates a fixture. Unknown reads/writes stay explicit gaps; ordinary Atlas frames remain read-only. Engine-only checks or exported notes are not UI coverage passes. Extend reusable adapters instead of duplicating engine rules or product markup.

The bench context selector also covers all nine app sport families (NFL/NBA/MLB first), with source-derived game defaults and stat fixtures. Unsupported decisions/surfaces stay explicit gaps; existing TV-event-based athlete/detail/history projections and reveal wording are review targets, not certified sports UI. See the bench guide before extending adapters.

The bench's Game type selector discovers show-wizard bases and sport defaults. Its spec-derived input contracts live in `tools/gameplay-bench/game-controls.cjs`: use roster/best count, whole-roster size, picks, questions or grids as appropriate; never force starter/bench semantics onto every game. Five show fixtures are connected (lineup, best ball, Outlast, fresh picks, survival pool). Other families are selectable adapter gaps that clear stale previews. Sports league/recipe counts are not counts of distinct game types. Multi-pick history/commands are supported, but the current production quick editor's single-choice limitation remains a coverage gap.

Before expanding the bench further, read the [scenario explorer implementation plan](docs/PLAN-GAMEPLAY-SCENARIO-EXPLORER.md). Follow its dependency-ordered chunks: a shared versioned scenario, capability/adapter composition and three-case proof precede further recipe expansion. Foundation, runnable breadth, product interaction, design review and user approval are distinct milestones; missing adapter labels are unfinished runnable coverage, not completion.

Explorer chunks 0–2 and Chunk 3's headless core have an [implementation guide](docs/GAMEPLAY-EXPLORER.md): v2 schema, lossless v1 archive, arbitrary-spec analysis, scoped planning, shared seeded worlds/stores, production projections/actions, atomic traces, explicit clocks and pinned checkpoint/replay. `node scripts/gameplay-bench.js execute --file=<scenario or execution.json> --out=<new result.json>` runs without recorded data, a browser or DB. CLI, HTTP and the stateless `window.__GAMEPLAY_EXPLORER__` browser transport call the same runtime. The visible bench now opens v2 definitions in the same runtime and, by default, materializes them as local zt-gb- rows so its frames read and write the REAL routes (`tools/gameplay-bench/live-db.cjs`; the user's decision, plan §3.4: never grow hand-shaped responses for new surfaces); snapshot reconciliation and caching remain before calling Chunk 3 complete. Three-definition checks are headless, not Chunk 4 browser/UI passes. Unknown modifiers/sports stats generation remain gaps. Keep tests focused between changes and broaden at meaningful milestones, per user preference.

The explorer is for both manual use and unattended automation, including future long-running broad search campaigns. Design headless runtime/result/cleanup contracts from Chunk 3; Chunk 4A's resumable campaign runner exists for the engine/state tier (`node scripts/gameplay-bench.js campaign`, docs/GAMEPLAY-EXPLORER.md#campaigns); final scaling waits for Chunk 12. Require stable case IDs/seeds, durable checkpoints, worker isolation, bounded resources, failure minimization and separate attempt/case/coverage accounting. Large engine runs do not establish UI/design approval, and this preference does not itself request starting a long-running campaign now.

The bench now includes actual episode reveals with direct lineup/standings entry, the current creation wizard with its selected generated lineup recipe (inspection only), and independent viewing marks for each player. A viewer switch must retain that person's mark; a reveal advances only that person across the episode's games. Own-pace catch-up writes use the engine's viewer copy; live-only is explicit. Keep the current wizard baseline while designing its eventual overhaul; do not treat it as a new wizard or claim its edits already drive the running preview.

## Visual asset tooling

Codex and Claude Code can use the `nano-banana` MCP server for generating and editing icons, user interface mockups, and visual assets. Consider it when an image-generation or image-editing tool would help the task. Use Impeccable for visual design, Intent for UX design and strategy, and Perception-First Design for perceptual hierarchy; asset generation supports those decisions.

- Codex connection: the user's `~/.codex/config.toml`, under `[mcp_servers.nano-banana]`.
- Claude Code connection: this project's `.mcp.json`, under `mcpServers.nano-banana`. `CLAUDE.md` imports this file, so this guidance applies to both agents.
- Server launch: `npx -y @seungmanchoi/nano-banana-mcp@1.2.1`, with `GEMINI_MODEL=gemini-3.1-flash-image`. The unscoped `nano-banana-mcp@1.0.3` hardcodes a retired preview model and fails generation with HTTP 404; do not switch back to it. Authentication uses `GEMINI_API_KEY`; the shared Claude configuration references that environment variable. This machine supplies it through the ignored `.claude/settings.local.json` environment settings. Keep actual credentials in private local configuration or environment variables.
- Configuration does not prove a live connection. Discover the tools exposed in the current session before claiming access or successful generation. If unavailable, report that accurately; do not claim the server produced an asset it did not generate.
- Cache every generated project image for reuse. Candidate implementation assets live under `public/art/generated/` with versioned filenames and a provenance manifest; see `docs/VISUAL-ASSETS.md`. Reuse saved bytes when implementing an approved study instead of regenerating. Keep previous versions when a deliberate visual change is requested. Never put credentials or private user data in asset metadata.
