# Gameplay bench

Mode: Operate. A local extension of the UI Atlas, inheriting its dark ink, warm yellow active controls, quiet borders and system UI typography. No change to the product's visual identity.

The frequent task is generating a reproducible game situation, interacting with the actual app, inspecting its data and exporting evidence. Keep scenario selection, Generate, surface, viewport, theme, Reset and export within reach. The real game preview leads the central workspace; compact settings occupy a left rail, inspection is progressively disclosed below/right. Small screens stack controls before the preview and allow local scrolling of fixed-width previews.

One clear primary action generates the scenario. Changing a form value marks it unapplied; it must not silently discard choices in the active game. Presets fill the form and generate deliberately. Renderer scope, synthetic data, unimplemented adapters and engine-only checks stay explicit. Do not label checks as a UX pass or user approval. A seed, configuration and command log reproduce the same state; replay is an intentional action. Error messages preserve the current preview and explain recovery.

No new images: recorded show artwork and real production components provide the app preview's identity. Bench expression comes from precise alignment, strong selected states, tabular measurements and uncluttered control groups. Bounded QA: one desktop/mobile inspection batch and at most one confirmation batch.

The next extension adds Episode reveal and Create game alongside the existing surfaces, with contextual episode/beat controls. Clearly distinguish replaying a watched episode from advancing the selected person's progress; no per-game reveal selector. The expandable pace readout explains independent marks and offers View as directly. Own-pace is the default, with an explicit live-only comparison. The creation surface preserves today's wizard as an inspectable baseline with the selected lineup/scoring recipe; editing it does not change the running game and creation remains blocked.

Game type is now a first-class control for shows and sports. Discover show bases from the production wizard and sport games from production defaults. Derive quantity fields from the spec's acquisition and count mechanics: lineup slots, roster/best count, whole-roster size, picks, question definitions or grid dimensions. Never display starters/reserves for a game that does not use them. Fixed sport defaults are visibly read-only; an unsupported family is a selectable, explicit adapter gap with no stale preview. Counts refer to fixtures, not distinct game types or design passes. Keep known production editor limitations (including multi-pick interaction) separate from engine fixture support.

## Redesign brief (2026-11-12, plan §6A step A; impeccable only: Intent and PFD aren't installed for Claude, so their questions are a checklist below)

- **Job and audience.** Conor (and any agent) testing the real app with generated situations: open a case, set who is watching and what has happened, look at the real screens (one app version, or two side by side for a redesign), act in them, and read the evidence. Operate mode, desktop first; phone is a quick look. Campaign failures open here for diagnosis.
- **Outcome and proof.** In one view: whose eyes, which moment, which app version, which screen, and whether the server and runtime agreed. Real captures in real phone frames; evidence as plain statements (agreement, spoiler scan, UI checks), never a "passed" badge for design.
- **Direction.** Inherit the Atlas world (ink, warm yellow for the active control, quiet lines, system type, tabular numbers). Three columns: Situation (people and their marks; the episode timeline with Air, Publish and Reveal) on the left; screen tabs, app version and the device frames in the middle; Evidence on the right. A case bar on top names the case and its source (definition, campaign case, recipe).
- **Scope.** One reviewable mock page with variants: single version; side by side; a campaign failure opened; a blocked definition; phone. Static mock with real captures; the working shell follows only after review. The legacy recipe form moves behind "Open…" ("Start from a recipe").
- **States.** 1–4 people at different marks; 3–6 episodes in released, partial, airing-next and future states; 1–3 games; renderers from 1 to 6; empty evidence, agreement mismatches, spoiler leaks, blocked definitions, failed reads.
- **Intent checklist (task flow).** Open → situate → look → act → inspect → export, with no step needing JSON. Every runtime control says what it changes (the viewer's mark, the scenario clock, the shared results). Compare keeps both sides on the same case, viewer, screen and step.
- **PFD checklist (first view).** At a glance, before anything else: the case and its source, the viewer and their mark, the app version(s), and any disagreement or leak. Secondary detail (trace, definition, missing reads) is one click away.
