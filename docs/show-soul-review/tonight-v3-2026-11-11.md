# Tonight V3: your results, the couch and the reveal

**Superseded by [V4](tonight-v4-2026-11-11.md).** V3 incorrectly assumed that games could be selected individually for reveal. The user's clarified rule is that revealing an episode reveals results across all applicable games, with a full-screen recap and game/player presentation. The historical description below is retained for comparison, not as current product direction.

## Overview and detail

Each game now carries a compact last-episode result alongside the next action. The captured episode-3 examples show the viewer's survival pick and **+1.5** lineup contribution, with Riley's shared **+0.5** available for comparison. Every action includes its own episode, so after a partial reveal one game can say **Pick E4** while another still says **Reveal E3**.

| Entry | Direct destination | Return behavior |
| --- | --- | --- |
| Game name | Existing full game page | Opens separately; Tonight and local choices remain in place |
| Your last-episode metric | That episode's game comparison | Returns to Tonight without changing progress |
| Another player's metric, name or avatar | That player's episode/game context | Returns to the same comparison or showcase chapter |
| A score | Starting-lineup/pick contribution breakdown | Returns to the same result |
| Participant in the recap, picker or contribution | Participant detail with captured show facts | Preserves the draft selection, dialog scroll and previous detail |
| Contribution value | Captured reasons and counted/excluded context | Returns to the same score breakdown |
| Episode results & recap | All available game results plus recap/showcase entry | Unrevealed games remain explicit; no automatic reveal |

The general connected-overview rule now lives in PRODUCT.md and APP-REVIEW-DESIGN-BRIEF.md. This pilot demonstrates it; other production overviews still need the same treatment during their review.

## Reveal choice

The added **tonight.reveal-ready** atlas recipe deliberately separates watched progress (episode 3) from each game's revealed progress (episode 2). It is a derived fixture, not a production state migration.

Opening Reveal first presents the episode, the affected games, and two presentations:

- **Showcase:** four manually paced chapters: the episode, your games, the couch comparison, and GIF reactions. Chapter selection, Back/Next and arrow keys are available; no auto-advance. People, scores and cast members remain interactive. Returning from detail resumes the same chapter. Adding a GIF returns to the reaction chapter.
- **Quick summary:** the same permitted recorded results in a scannable view, with score and player drill-downs. A single selected game's summary stays scoped to that game. A multi-game summary can also show other games as still hidden.

Only the explicit **Reveal N games** confirmation advances the selected browser-local game marks. Canceling changes nothing. Neither presentation changes watched progress, and switching presentation does not reveal more games. A replay changes no progress.

Revealing one game's episode can make the already-watched show's recap available, while the other games' scores stay hidden. It does not force every game into sync. Next actions continue to use each game's own episode.

## Data and visibility

Episode 3's reveal payload is a bounded export of the existing local recorded fixture: that episode's outcomes and game histories through episode 3. It is fetched only after explicit confirmation. No later outcomes are included. The payload is read-only review material; it is not a protected production endpoint or an authorization mechanism.

The default catch-up view can replay its already-revealed episode from its effective atlas data without fetching a new reveal payload or marking anything revealed. The new reveal-ready case uses the saved recorded episode-3 payload after confirmation. Other episodes are explicitly unavailable in this review rather than receiving invented results or recomputed outcomes for local preview choices.

Opponent results are shown conservatively from explicit per-game pace metadata. The viewer's mark must allow that episode, and an opponent's next game episode must put the result within their revealed history. In this fixture Riley's episode-3 result is available, Sam is behind, and Jordan's per-game reveal status is unknown. Both behind and unknown results remain hidden even though the captured projection contains rows for them. Watching progress alone is never used to authorize game choices.

Scores and comparisons are **per game, per episode**. No cross-game point totals or global ranks are fabricated. Weekly Lineup contributions use captured totals, starter and bench rows. The reasons list does not invent an allocation of the contribution total among individual reasons. General show facts remain distinct from game scoring. Social messages, friendly identities and GIF reactions are still illustrative and labeled in the preview notes.

All marks, GIF choices and other interactions stay in browser-local state. The actual game engine, production reveal endpoints and timing defaults remain unchanged. Full-game links open the current application with its captured case state; local mock reveals are not written into that application.

## Skill reasoning

**Intent:** The player needs the payoff of the previous episode as well as the next decision. Give each simplified result a direct path to its evidence. Separate choosing a presentation from committing a reveal, and preserve the exact return context.

**PFD:** Shared, episode-labeled result lines support comparison without importing full standings into Tonight. The reveal gate makes the scope and consequence visible before the outcome. A progress-preserving return removes the need to reconstruct the previous context. These are applied design hypotheses, using the existing [PFD derivation](perception-first.md), not new usability measurements.

**Impeccable:** Retain artwork, recognizable cast photos, bold typography, the GIF wall and existing palette families. Use the saved island artwork for the showcase. Give results a clear typographic hierarchy and keep the overview actions reachable in the tested first mobile view. Reduced-motion behavior remains available. No assets were regenerated.

## Production integration still required

The current `src/new/show/reveal.tsx` opens a show-wide broadcast that calls the reveal mutation before presenting its beats. The own-pace catch-up path in `pace-plate.tsx` / `join-game.tsx` reveals an individual game and shows a result sheet. The proposed shared scope/style choice must reconcile those paths; a visual wrapper must not accidentally call the show-wide mutation when only one game was chosen.

Use a server-authorized result presentation model and explicit mutation scope for both summary and showcase. It should carry each game's episode, result stage, counted contributions, permitted opponent choices and replay status. The engine's generated game structures must supply the appropriate result components. Do not generalize the pilot's Survival Pool and Weekly Lineup metric adapters to every GameSpec combination without those contracts. Authorized scopes, retries, final/provisional updates, and replay behavior need server/engine checks during implementation.

## Verification

`node scripts/dev-test/check-tonight-results.js` exercises three cases at 390×844, 360×700 and 1100×900. `--no-captures` repeats functional checks without saving the initial screenshots again.

Checks cover the last-episode insights; behind/unknown opponent masking; selection → participant → return; comparison → score → participant/contribution → return; showcase chapter retention; GIF return; cancellation; one-game and multi-game reveal scope; switching presentation; unchanged watched progress; mixed per-game next targets; preserved V1/V2 hashes; and version/case selection in the atlas. The captured fixtures have no horizontal overflow or broken images, and the required initial overview controls fit above navigation on both phone sizes. The complete GIF wall and detail screens may scroll. Browser checks report no errors or app-API writes.

Atlas unit checks also cover the reveal-ready projection's separation of watched and game-reveal progress, preserving the viewer's recorded choice, removing unrevealed result rows, and leaving couch-level game cards alone. These checks are bounded UI evidence, not authorization certification or proof that all generated game formats are understood.

Screenshots and machine-readable evidence live under `.ui-atlas/tonight-pilot-v3/`. This iteration awaits user review before extending the design to other surfaces.
